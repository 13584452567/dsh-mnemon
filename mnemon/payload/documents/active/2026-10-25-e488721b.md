# 投屏隐藏文档黑屏：保留合成表面 + 管线停滞看门狗

相关设计：投屏呈现恢复状态机与 APP_SWITCH 和弦控制，id `8f130951-1500-4159-8e8f-8e106efe5232`（本文替换其中“250ms 去抖后真正分离”的做法，其余位图回退与和弦控制不变）；直连 USB 占用问题与“投屏遮挡恢复未修”记录，id `c6aa8e7b-f2bf-487f-87b2-18dead97d3f0`（本文覆盖“隐藏文档 → 重新显示”这一条路径，窗口遮挡/最小化仍未单独验证）。

## 现象与根因

切到别的标签再切回投屏文档：属性面板仍显示“投屏中”，控制 socket 正常（按键/触摸可用），但视频画面冻结且永不恢复。

`ScreenMirrorGpuPresenter` 原本在可视对象离开可视树 **250 ms 后拆除合成表面**。直连 USB 的 GPU 零拷贝路径中，解码帧由合成表面消费；表面一拆，解码器的导出环失去消费者：帧被丢弃、`MarkPresented` 不再发生，解码器随即停止产出帧。因此“设备侧还在推流”与“界面还在投屏中”同时成立，却没有任何一帧被呈现。

诊断行证据（切换标签后）：

- `bytes` 持续增长（8.2 MB → 14.2 MB，视频数据一直在到达）
- `decoded`/`presented` 冻结在 87/83
- `surface=True hasFrame=False`

说明停摆在呈现侧而不是设备/协议侧。

## 修复

1. **隐藏文档不再拆除合成表面**：`ScheduleDetachCompositionVisual` 只把呈现标记为暂停（`_hostDetached`），表面、interop 导入与表面视觉对象继续由呈现器持有；真正关闭文档仍由 `DetachCompositionVisual`/`Dispose` 释放。再次显示时走复用路径重挂视觉对象并请求关键帧，下一帧直接呈现。
2. **管线停滞看门狗**（兜底任何路径下的静默黑屏）：有视频字节到达但 1.5 s 无新解码帧 → 请求关键帧（750 ms 节流）；5 s 仍无解码帧 → 以可恢复错误触发一次解码器重建（Windows 上从 GPU 导出降到 CPU 回读）。
3. **删除已失效的延迟分离令牌机制**：`ScreenMirrorCompositionRecovery.ScheduleDetach/IsDetachCurrent/CancelDetach`、呈现器的 `DetachDebounce`/`_detachTimer` 及对应用例。隐藏语义改为“暂停呈现 + 保留表面”，不再需要去抖竞态处理。

## 真机 GUI 实测（05C6:90DB）

采样方式：视频区域平均亮度 + 变化像素数（共 569232 采样点）。

- 修复前：切走 3 s 再切回，平均亮度 **44.4 → 4.83**（max 49），145913 个采样像素变化；保持 12 s 仍为 4.83，黑屏不恢复。
- 修复后：**72.68 → 72.59**（max 255），仅 832/569232 像素变化（时钟级）；随后注入“主屏幕”，视频区变化 **126659** 采样像素，证明画面实时更新且控制可用。
- 最终二进制复跑：**44.52 → 36.50**（max 255）、62952 采样像素变化（正常画面刷新），无黑屏。

`VERIFICATION.md` 已追加本轮实测记录。

## 门禁

- `dotnet restore UotanStudio.slnx -p:Configuration=Debug` + `dotnet build UotanStudio.slnx --no-restore --nologo -c Debug`：0 错误。
- 期间遇到的两类环境失败（非代码缺陷）：
  - `CS1061 AttachDeveloperTools / AttachDockDebugOverlay`：并行会话以空 `$(Configuration)` 还原导致 `Dock.Avalonia.Diagnostics` 编译资产被剔除；按 AGENTS.md 显式 `-p:Configuration=Debug` 还原后消失。
  - `CS2012` 无法写 `obj/Debug/net10.0/UotanStudio.pdb`：被另一个 `MSBuild.exe` 锁定；结束占用进程后可正常构建。
- 定向测试：Media 202/203（1 Linux 跳过，删除 2 个失效用例）、Mirroring 111/112（1 真机门控跳过）、Devices 245/245、Architecture 16/16。
- `dotnet format` whitespace 与 style 两道门：零报告。修复前两处格式错误（`ScreenMirrorGpuPresenter.cs` 多余空格、`ScreenMirrorCompositionRecovery.cs` 文件末尾换行）。

## 未验证边界

- 本机只有一台真机，未用两台设备同时开两个投屏标签逐一切换；已验证的是完全相同的“隐藏文档 → 重新显示”路径，且诊断证明停摆发生在呈现侧。
- 隐藏的投屏文档现在会保留一份合成表面（换取秒开与不丢帧），未做多文档长时间显存压测。
- macОS IOSurface 与 Linux VA-API 导出路径按同一机制受益，但未在对应平台验证。
- GUI 实测跑在包含完整修复的构建上；最终构建仅多出死代码删除与注释更新，行为一致。
- 窗口遮挡/最小化后的恢复（`c6aa8e7b` 中记录的未修项）本轮未涉及。
