# 直连 USB ADB 端点租约互拆与投屏不恢复：共享会话池修复与真机验证（2026-10-25）

本轮把“日志抓取与投屏互相拆会话 / `returned no lease` / 占用者清单为空 / 刷新详情卡约 5 s / 全局日志被 `[Debug] Exception` 刷屏 / 覆盖或最小化后投屏画面不恢复”收敛到宿主侧的三条结构性缺陷。前序轮次的结论见 `c6aa8e7b-f2bf-487f-87b2-18dead97d3f0`（Comm 层释放占位）与 `a8f55ea5-bea4-4769-840d-683303866320`（外部读者共享接口、路由 fail-closed）；本文只记录本轮的根因修正、实现与实测，避免与上述文档重复。

## 一、根因

1. **直连 USB ADB 端点被每个消费方各开一份独占租约**：日志抓取、详情补全、root 探测、shell、投屏各自 `OpenAdbLease`。冲突时旧实现直接强制摘除对方租约（`ReleaseStubbornEndpointHolders` + 升级重试），于是日志抓取与投屏会互拆会话；端点清理卡住时表现为 `returned no lease`。日志里 `still held by ;`（占用者为空）正是这条路径的诊断缺陷：只报了活动租约，没报释放中占位/被摘除者。
2. **root 探测在 UI 线程上同步取租约**（`EnrichAdbInfoAsync` → `HasSuAsync`），刷新详情卡约 5 s；此前的“后台化”只覆盖了 MTK/EDL 分支。
3. **`FirstChanceExceptionLogger` 无条件记录**被正常捕获的 `TimeoutException` / `OperationCanceledException`，全局日志被 `[Debug] Exception` 淹没，掩盖真实故障。

## 二、实现要点

- `DeviceMonitorService.SharedAdb.cs`：新增**共享直连 ADB 会话池**（引用计数；断链会话立即出池；打开失败丢弃不缓存；退出统一释放）。日志、shell、属性查询、root 探测与**投屏服务端**全部借用同一条连接。
- `OpenAdbLease` 不再强制摘除占用者；占用诊断始终写出具体占用者。删除 `ReleaseStubbornEndpointHolders` 及其升级重试路径。
- `ManagedMirrorSession` / `StartScrcpyOverUsbSession` 增加 `ownsAdbSession`：共享会话由借用作用域归还，投屏不再直接释放连接（修掉跨子系统互拆）。
- 投屏恢复：窗口激活、最小化还原、Dock 文档重新挂载时重挂合成表面并请求关键帧（750 ms 节流）；静默 5 s 补一次关键帧请求；会话结束状态不再停留在“投屏中”。这一项补上了 `c6aa8e7b` 中明确标注“未修”的遮挡/最小化恢复。
- 日志自愈：抓取失败或无输出时按 5 s → 60 s 退避自动重连；单 tick 上限 250 条 / 64 KiB；清日志不再重启抓取。
- 详情补全的属性批次与 root 探测全部留在工作线程。
- `FirstChanceExceptionLogger` 默认关闭，仅在 `UOTAN_FIRST_CHANCE_LOG=1` 时记录。

## 三、验证（真机 05C6:90DB，USB 直连，无 adb server）

- 构建：`dotnet build UotanStudio.slnx --no-restore -c Debug` 0 错误（仅 2 条既有 xUnit 分析器警告）。
- 测试：Devices 245/245、Mirroring 111/111（1 硬件跳过）、Media 204/204（1 Linux 跳过）、Architecture 16/16、FirstChance 6/6；whitespace 与 style 两道门零报告。
- GUI 两轮：
  - 设备详情读全序列号/品牌/Qualcomm/Android 9/SDK 28/arm64-v8a 与“1 个设备已发现”；
  - 投屏期间设备日志持续出新行（滚到顶再回到底后最新行与当前时间差 ≤ 20 s）；
  - 投屏 `投屏中` / H264 / Media Foundation (GPU) / 1440 × 2880，日志有 `Composition presentation active: D3D11 shared texture`；
  - 记事本覆盖 6–7 s 后切回：视频区像素差异 15768–29657 px、属性区 0 px；再注入“主屏幕”视频区再变 21940 px → 画面恢复且控制可用（可作为“投屏恢复”的可量化判据）；
  - 刷新详情后 UIA 查询 659 ms 返回、`targetResponsive=true`；
  - 全局日志全程仅 Info 与一条关键帧 Debug，无 Exception/Warn/Error；两次关闭均干净退出。

## 四、未验证边界

HDC/ohscrcpy 路径；server 路由下投屏与其它操作的并发；用户 04:45 报告的原始时序；>1 h 长时共存与拔插重连；NativeAOT 发布；macOS/Linux。均未在本轮执行，结论已同步写入 `VERIFICATION.md`。

## 五、复现与判据

- 复现互拆：投屏开启的同时打开设备日志并滚动、再刷新详情；旧实现会出现 `returned no lease` 或投屏黑屏，新实现应保持两条通路同时工作。
- 判据：视频区像素差 > 0 且属性区为 0 表示画面恢复而非布局重排；UIA 查询耗时 < 1 s 表示详情补全未阻塞 UI 线程。
- 若仍需定位占用冲突，先看 `still held by` 是否带出具体占用者，再看共享池借用/归还配比，而不是重启抓取。
