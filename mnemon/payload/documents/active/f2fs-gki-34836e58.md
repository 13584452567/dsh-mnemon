# F2FS 真实镜像重打包容量账目缺陷与 GKI 往返验证结论

范围：对真实 10 GiB F2FS `userdata` 镜像（F2FS v1.16，volume `data`，features `0x1499`，可达条目 3 个，含 1.587 GB `preinstall/cust.img`）执行托管解包 → 重建 → GKI 挂载/读写/fsck 往返。当前验证记录同步在 [VERIFICATION.md](VERIFICATION.md) 的「F2FS 真实镜像与 GKI 往返」小节。

## 阻断性缺陷与根因

原始实现的 `F2fsBuilder.ComputeLayout` 只用「节点段 + 数据段 + 8」决定主区段数，而 checkpoint 另按 5% overprovision 扣减用户容量。有效数据超过约 230 MB 后，重打包镜像出现容量账目倒挂：

| 项目 | 修复前 | 修复后 |
| --- | --- | --- |
| 重打包镜像大小 | 1,629,487,104 B | 1,704,984,576 B |
| `user_block_count` | 370,688 | 388,608 |
| `valid_block_count` | 387,863 | 387,863 |
| `free_segment_count` / `rsvd_segment_count` | 6 / 6 | 42 / 6 |
| GKI 5.10 / 6.6 / 6.18 | 挂载失败 `Wrong valid_user_blocks` | 三版全部 PASS |

关键教训：`fsck.f2fs` 对该 `valid_block_count > user_block_count` 情形返回 0 且不报错，因此 fsck 通过不能作为重打包容量正确的充分门；必须由内核实挂（或在容量回归测试中断言账目）来判定。对照实验以固定 `SegmentCount=1200` 重建后 GKI 5.10 可挂载，确认根因是主区段数而非元数据内容。

## 修复点

- [F2fsBuilder.cs](UotanStudio.Firmware/FileSystem/F2fs/F2fsBuilder.cs)：按有效块（含压缩保留块）反推主区段数，使扣除 overprovision 后的 `user_block_count` 覆盖全部有效块。
- [F2fsBuilder.Metadata.cs](UotanStudio.Firmware/FileSystem/F2fs/F2fsBuilder.Metadata.cs)：overprovision 百分比收敛为单一常量，容量预算与 checkpoint 写入共用同一参数，避免两处口径漂移。
- [F2fsParser.cs](UotanStudio.Firmware/FileSystem/F2fs/F2fsParser.cs)：`DeviceId` 仅对字符/块设备 inode 读取，不再把常规文件首个数据块地址误当设备号。
- [F2fsTests.cs](UotanStudio.Tests/Firmware/F2fsTests.cs)：新增 320 MB 载荷的容量回归测试 `Build_LargeData_CheckpointCapacityCoversEveryValidBlock`（断言容量账目与保留段），并断言常规条目 `DeviceId == 0`。

## 验证证据

- 内核 `5.10.269-gd071d2b9ad81`、`6.6.143-gc8fde724315a`、`6.18.32-g8efe853aba9b`（QEMU TCG，无 `/dev/kvm`）各自完成：fsck(源) → fsck(重打包) → 双向只读挂载 → 3 条目树对比 → mode/uid/gid/size/atime/mtime/ctime 与 `security.selinux` 对比 → `cust.img` SHA-256 与源一致 → 读写挂载写 512 B 与 2 MiB → 卸载 → fsck → 只读重挂载 → 写回哈希校验 → dmesg 检查，三版均 `RESULT PASS`，btime 两侧均为 `0.000000000`。
- 测试门：F2FS 相关 7 个测试类 70/70 通过；`UotanStudio.Tests.Firmware` 全命名空间 4301 项 / 4299 通过 / 0 失败 / 2 跳过（跳过项缺 `UOTAN_EROFS_CORPUS`）；改动文件 whitespace 与 style 的 `dotnet format --verify-no-changes` 通过。
- 证据目录（镜像已清理，保留日志/报告）：[report.md](artifacts/gki-fs-lab/f2fs-real-20261024/report.md)、[report.json](artifacts/gki-fs-lab/f2fs-real-20261024/report.json)；`logs/qemu-prefix-*.log` 为修复前挂载失败，`logs/qemu-fixed-*.log` 为修复后三内核 PASS，`logs/qemu-capacity-control-5.10.log` 为容量对照实验。

## 已知边界

- 重建不保留源超级块特性位（`0x1499` → `0x58`，丢失 encrypt/verity/casefold/quota_ino），也不重建 quota inode/限额、物理分配与稀疏布局；源无 crtime，重建写 0。
- 该镜像本身没有硬链接、符号链接、设备节点、压缩、大小写折叠、加密或 verity 内容，这些路径仅由合成夹具与单元测试覆盖，未在真实镜像上验证。
- QEMU 为 TCG 软件执行，不代表真实设备或厂商内核的挂载/性能表现。
