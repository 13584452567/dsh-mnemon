# UotanStudio 编解码/常量权威收敛（依赖清理第 1–5 批）

完成于一次宿主 + 固件层的重构会话。目标是把"第三方编解码库、重复魔数与哈希常量、ZIP 结构写入"收敛到唯一权威项目，并用架构守卫测试把规则固化下来，防止回潮。仓库根 [AGENTS.md](AGENTS.md) 的依赖下降规则是判定依据。

## 落地的五条权威

1. **第三方压缩库只允许出现在 `UotanStudio.Compress`**
   - 新增 `UotanStudio.Compress/Codecs/Zstd/ZstdEncoder.cs`、`ZstdDecoder.cs`：级别/字典/checksum/windowLog、`MaximumCompressedSize`、流式 `Decompress` 与状态。
   - `Codecs/Lzma/LzmaEncoder.cs` 暴露 `Configure(dictionarySize, posStateBits, litContextBits, litPosBits, algorithm, numFastBytes, endMarker)`；`LzmaDecoder.cs` 提供 `SetProperties`；`LzmaEncoderStream`/`LzmaDecoderStream` 是唯一字节流入口。
   - 迁移面：Comm HDC LZ4、ADB sync v2（LZ4/Zstd/Brotli 全走 `CompressionService`）、F2FS、SquashFS、EROFS（LZMA 参数 + zstd 池）、Payload REPLACE 解码与 Builder 并行压缩、NTPi LZMA2。
   - F2FS/EROFS 去掉了对 `K4os` 的直接引用（EROFS 改用 `Lz4BlockCodec` 计长与解码），避免"引了不用"的假依赖。
2. **FNV-1a 归 `UotanStudio.Hash`**：新增 `UotanStudio.Hash/Fnv1a/Fnv1a64.cs`（`Compute(char/byte span)`、`Compute(span, basis)`、`Mix`）；`UotanStudio.Comm/Devices/Services/DeviceController.cs` 的 `MixModeItem` 改调它。
3. **ZIP 结构权威在 `UotanStudio.Compress/Zip/ZipContainer.cs`**：新增 `AppendArchiveComment`（校验 EOCD、拒绝已带注释或注释含 `PK\x05\x06`）与 `ValidateSingleDiskLayout`（单盘、非 ZIP64、无加密、仅 stored、目录连续）。`UotanStudio.Delivery/Build/Package.cs` 的 `SignAsync` 与 `UotanStudio.Projects/VisualPlugins/VisualPluginBundle.cs` 预检改为调用这两个方法。**ZIP64 原始范围读取与原地 CRC 修复仍留在 Delivery**，因为签名依赖其原始偏移能力。
4. **格式魔数权威在 `UotanStudio.Firmware/Core/BlockImageMagic.cs`**：`SparseFormat.SparseHeaderMagic` 改为引用它，替换 6 处重复字面量。
5. **命名去歧义**：`Oppo/Parsers/FormatDetector.cs` 重命名为 `OppFormatDetector.cs`，消除与 `Core.FormatDetector` 的同名歧义（该文件在原工作区里是先删除后重建）。

## 非显然的架构约束（关键理据）

- **稀疏魔数必须放在 `Firmware/Core`，不能放在 `Firmware/BlockImage`**：架构测试把 `FileSystem -> BlockImage` 列为**已撤销的循环边**，`FileSystem` 侧直接引用 `BlockImage.Sparse` 会被架构用例拦下。所以权威常量落在两者都能引用的 `Core`。
- 守卫测试是 `UotanStudio.Tests/Firmware/Architecture/CodecAuthorityGuardTests.cs`（4 条）：Compress 之外不得引用 ZstdSharp/K4os/SharpCompress/SevenZip；FNV 常量只能在 Hash；稀疏魔数只能由 `BlockImageMagic` 书写；只有 ZIP 权威能定位/写出 EOCD。
- 白名单必须逐条写明理由，目前保留：ArchiveBrowser（SharpCompress 多格式读取器）、BinaryDeltaPatch（bsdiff 的 bzip2 段）、Delivery（ZIP64 原地修复）、APK 原地成员改写、头部探测。新增白名单条目要附理由，否则等于绕过守卫。

## 验证（实测）

- `dotnet build UotanStudio.slnx --no-restore --nologo -c Debug` → 0 error。
- `dotnet format UotanStudio.slnx whitespace|style --no-restore --verify-no-changes` → 干净（注意 `.editorconfig` 是 `insert_final_newline = false`，format 报 `FINALNEWLINE` 时是**文件多了**尾换行，要删）。会话中先出现 12 个 FINALNEWLINE 报错，逐文件裁剪后收敛。
- 全量测试：7639 总计 / 0 失败 / 7 跳过（此前 7634，+4 条新守卫 +1 条并行改动）。定向：Firmware 4378、Protocols 119、Delivery 176、Devices 321、Architecture 55 全通过。

## 未验证 / 边界

- `dotnet publish UotanStudio.Desktop/UotanStudio.Desktop.csproj -c Release -r win-x64 --self-contained`：**无 IL2xxx/裁剪告警**，但在复制 PDB 阶段以 `MSB3030` 失败。原因是工作区既有 Release `DebugType=none` 与默认发布复制清单的冲突，与本次改动无关；原生镜像产物未核对，需单独确认这次 publish 失败是否可接受。
- 真实设备与厂商互操作（HDC/ADB 实机、NTPi、Ozip、OPS）、EROFS QEMU 语料未跑，对应用例需 `UOTAN_HDC_MIRROR_DIRECT` / `UOTAN_EROFS_CORPUS`，属被跳过的 7 条之一。
- 后续候选：`ArchiveBrowser` 与 `BinaryDeltaPatch` 的两处直连仍未收敛（守卫已带理由登记）。
- 会话期间有另一并行会话在改未跟踪的 `UotanStudio/Services/Firmware/AvbOtaService.cs`、`UotanStudio/ViewModels/Shell/AvbToolViewModel.cs`，宿主一度编译失败（`AvbOtaService` 被声明为 `static class` 却按实例注入）；待其收敛后重跑构建与全量测试才得到上述数字。改动这两处前先确认并行线是否仍在进行。
