# 瑞芯微「存储介质」真实对应与 cfg 字段边界（2026-11 复核）

> cfg 二进制布局本身见文档 `887976bc-7e87-4a39-9f1e-53ce4d9fa407`（Rockchip 烧录页接线与 RKDevTool v2.96 config.cfg 结构）；本文只记录本轮复核得出的「哪些值是真事实、哪些是冒充事实」的结论与改动，不重复结构表。

## 1. 触发问题

用户提出两点：导入 cfg 时**文件不存在的行也必须出现在分区列表里**；以及**再次检查 cfg 文件结构，确认存储介质是否真实对应**。前一条是行为要求，后一条暴露了一个实现瑕疵：瑞芯微 cfg 行的 `StorageMedium` 曾是拿**面板下拉框当前选中项**去掉编号后盖上（`SelectedRkStorageLabel` / `ApplyRkConfigStorage`），而不是来自文件。

## 2. cfg 里没有「存储介质」字段（复核结论）

- 每行 610 B 只有三段有语义：名称（UTF-16 80 B）、路径（UTF-16 512 B）、尾块 16 B 的前 8 B 行地址；其余尾字节与头部日期块语义未确立，实现按原样保留、解析→序列化逐字节还原。
- 行内**没有介质、没有大小、没有勾选状态**；`Loader` 只是行名约定，不是专门字段。
- 仓库内无厂商源码、无更多 cfg 样本，因此尾块后半段与头日期块仍属未确立（已写入 `UotanStudio/Services/Flash/RockchipConfigFile.cs` 的 remarks）。

三点理由说明旧行为不成立：cfg 不存介质（非文件事实）；刷写路径 `FlashRkdlAsync` 从不发送 `CHANGE_STORAGE`，实际写到设备当前活动介质，面板选择只在点「切换存储」时生效（非运行事实）；该编号本身还与厂商协议不一致（见 §4）。

## 3. 现行约定：只有真来源才填这一列

删除 `SelectedRkStorageLabel` 与 `ApplyRkConfigStorage`；`ApplyRkConfigRows` 生成的瑞芯微行不再写 `StorageMedium`（留白），原因写进导入方法注释。列本身保留，只由可追溯来源填值：

| 来源 | 值 | 依据 |
| --- | --- | --- |
| MTK scatter 行 | `EMMC` / `UFS` | scatter 存储类型 |
| EDL rawprogram 行 | `LUN n` | `physical_partition_number` |
| 瑞芯微 cfg / 单镜像行 | 留白 | 文件与流程都未确定，不猜测 |

缺失文件的处理：`ApplyRkConfigRows` 仍为每条配置行发布一个分区行（`Name` 为空时退化为文件名），`CanSelect = File.Exists(path)`，缺失行 `StatusText` 用本地化键 `Flash_FileMissing`、大小为空 —— 即「列出但不可勾选」，不再因文件缺失而丢掉条目。

## 4. 顺带查出的编号对应问题（未改，只加证据注释）

- 仓库内 `RkStorageTypes`（`UotanStudio/ViewModels/Flash/FlashViewModel.Operations.cs`）用的是厂商 UI 列表编号 `1. FLASH … 10. PCIE`。
- 随仓库保留的 `reference/rkdeveloptool/main.cpp:59` 记载 `ChangeStorage: cs [storage: 1=EMMC, 2=SD, 9=SPINOR]`，与 UI 编号不同。
- `reference/rkdevtool/src-tauri/src/device_ops.rs` 明确把这份 UI 列表经 `storage_from_ui_no` 转换成**独立的协议枚举**（`StorageIndex::{Nand,Emmc,Sd0,Sd1,MtdBlkSpiNor,MtdBlkSpiNand,Ram,MtdBlkNand,Sata,Pcie}`，8 = `MtdBlkNand` 被标为 UI 上的 USB）而不是原样发送。
- 现有代码 `ChangeStorage((byte)(index + 1))` 发的是 UI 编号；`DescribeRkStorage(READ_STORAGE 的首个置位下标)` 又把协议下标当 UI 编号解释（`RkStorageTypes[storage - 1]`）。按上述证据两处都可能错位（例如设备回报 EMMC 会显示成「1. FLASH」）。

没有真机与协议表无法定论，因此只把边界写进 `RkStorageTypes` 与 `DescribeRkStorage` 的 remarks，不改行为。后续统一方案：拿到真机 `READ_STORAGE` 位掩码与 `CHANGE_STORAGE` 实测后建立单一映射表，并让刷写前真正下发切换。
