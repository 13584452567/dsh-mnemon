# ADB 无线调试 TLS 不支持服务端证书钉扎（Windows x64 / .NET 10，2026-10-26）

结论：设备侧 adbd 的 TLS 服务端证书**每次握手都不一样**，按 `host:port` 钉扎 SHA-256 在第二次连接时必然失败；主机侧只能“接受任意但仍必须出示”的服务端证书，真正的身份校验在设备侧对客户端公钥做。

相关文档：`b3f83b64-e6de-4c4f-b765-00d33be373e2`（CRC/CNXN/托管 TLS 死锁/单播 DNS-SD 三重根因）、`dddf19d9-142d-4ea5-a267-24369c23a9f0`（空闲读期限击穿托管 TLS 记录层）、`cd5e7bab-64ff-4918-887a-bab9cd978987`（配对后 adbd 重启 TLS 服务导致死会话复用）。

## 根因（上游源码依据，仓库内 `reference/adb-android16/`）

- `daemon/auth.cpp:358` `adbd_auth_tls_handshake`：每个 adbd 进程懒生成一把**随机 RSA 密钥**。
- `crypto/x509_generator.cpp` `GenerateX509Certificate()`：每次握手现造证书，`notBefore` 取**当前时间**、序列号固定为 1，因此 DER 每次连接都不同。
- `transport.cpp:540`：主机侧 `SetCertVerifyCallback([](X509_STORE_CTX*) { return 1; })` 接受**任意**服务端证书；被校验的是设备侧 `adbd_tls_verify_cert`（校验客户端公钥）。

症状链：扫码配对时的验证握手成功并记下指纹 → 下一次连接指纹不匹配 → 客户端在 `NotifyServerCertificate` 里主动抛 `bad_certificate(42)` → 设备尚未收到客户端证书，ADB 会话直接失败 → 设备行失效 → 投屏报 `Device <ip:port> is not connected`。日志里出现 `bad_certificate(42)` 且地址是曾成功配对的端口，即可判定为此问题而非配对失败。

## 修复（当前契约）

- `UotanStudio.Comm/Transports/Tcp/AdbTlsTransport.cs`：删除服务端证书指纹参数、观察者、`RemoteServerCertificateSha256` 与钉扎比较；平台栈（SslStream）与 BouncyCastle 两条路径都接受任意但仍必须出示的服务端证书，并在注释中说明 adbd 证书每次握手重建。
- 同文件新增 `ClientKeyRejection` / `internal static bool IsClientKeyRejected`：把设备回发的 `bad_certificate`、`certificate_unknown`、`unknown_ca`、`access_denied` 识别为“客户端密钥被拒”，转成可操作文案（重新扫码配对或接受设备调试授权）；握手路径与已建立连接的读写路径都覆盖。其它握手告警（如 `handshake_failure`）不判为密钥被拒。
- `UotanStudio.Comm/Devices/Services/DeviceController.Inventory.cs:156`：`OpenSecureNetworkAdbSession` 去掉钉扎参数。
- `UotanStudio/Services/Devices/DeviceMonitorService.Sessions.cs:378` 与 `DeviceMonitorService.Pairing.cs:207`：不再读取/记录指纹。
- `UotanStudio/Services/SettingsPersistenceService.cs:458`：`PairedNetworkTarget` 只保留 `Address`/`RequiresTls`；旧 `settings.json` 里的 `serverCertSha256` 被忽略，下次保存自然消失，无需手工清理。

## 回归测试

`UotanStudio.Tests/Devices/AdbTlsTransportTests.cs`：

- `UpgradeToTls_DeviceRebuildsItsCertificateEachHandshake_CompletesBothHandshakes`：回环 TLS 服务端**每次连接重建自签证书**（`CertificateRequest.CreateSelfSigned` + `LoadPkcs12(Exportable)`），连续两次 `UpgradeToTls` 都成功、都收到客户端证书且服务端证书指纹不同——该测试直接锁住“钉扎回归”会失败。
- `IsClientKeyRejected_*` 覆盖四种拒绝告警为真、`handshake_failure` 为假。

## 未验证边界

- 复测时机上 `192.168.1.144:40443` 已不可达（无线调试关闭或端口变更），**真机扫码直连 + 投屏未复跑**；需要在重新打开无线调试（必要时重新配对）后按原路径验证。
- USB 直连与无服务器 TCP 之外的配对失败路径（如设备端主动撤销授权）只有单元测试层面的告警映射覆盖。
- 该改动与同时段并行会话提交的 `58f42e63 "pin the server certificate …"` 标题相反：现在是有意不钉扎，提交说明若尚未推送应更正。
