# 扫码配对后自动发现连接端口 + 直连 ADB 日志传输失效修复（Windows x64 / .NET 10）

本轮完成两项相互独立的修复：主线是 ADB 扫码（QR）配对成功后不再要求用户手填连接端口；并行子代理修复了"无 server 直连 ADB 设备打开日志报错/进程名表永远读不到"。相关背景文档：`b1898c91-0104-446e-9ebf-b27f6dcb61c6`（ADB/HDC 远端连接与 `host:pair` 基础修复）、`ef57d6e3-b882-46a9-8645-6cd36cb43a18`（宿主侧共享 ADB 会话池）。

## 一、扫码配对后自动获取连接端口

### 根因

| 现象 | 根因 |
| --- | --- |
| 几乎每台设备都掉进"手填端口"面板 | 配对成功后才**重新开一次** mDNS 浏览去找 `_adb-tls-connect._tcp`，窗口仅 10s，且只按 IP 字符串匹配 |
| 真机常查不到 connect 记录 | 设备在配对结束后可能立即撤回该广播；纯 IPv6 广播与 IPv4 配对地址无法互相命中（旧 `SameAddress` 只认 IPv4-mapped） |
| 有 server 时更差 | `adb pair` 之后只**瞬间查一次** `devices-l` 等 server 自己的 mDNS 自动连接，几乎必然落空 |

### 设计要点（`UotanStudio.Comm`）

- **一次浏览同时收集两类服务**：`AdbMdnsDiscovery.WaitForPairingSnapshotAsync` 在配对会话的整个浏览过程中收集 `_adb-tls-pairing` 与 `_adb-tls-connect` 候选，并把"配对前就已看到"的连接候选一并带出；命中配对后保留 1.5s 宽限以收齐同批广播。配对一结束端口通常已在手，不再依赖"配完再找"。
- **候选先实时 TCP 探测再采用**：剔除已失效/未监听的端口，避免用旧广播去连。
- **直连路径发现窗口 10s → 20s**。
- **有 server 时不再瞬查一次**：`WaitForServerTargetAsync` 轮询 server 的 `host:devices-l`（最多 15s）等 server 自己完成 mDNS 自动连接，**同时**用已发现端口并行执行 `adb connect`，先成功者胜出（`Task.WhenAny` + linked CTS，finally 中取消并吞掉输家的完成）。
- **同一设备双重识别**：`SelectConnectPorts`/`IsSameDevice` 按 **SRV 主机名或地址**匹配，解决双栈手机对不同服务返回不同地址族、以及同网段多台设备误配；候选按"主机名命中优先"排序并去重。
- **设备模型携带服务类型**：`MdnsDevice`/`AdbServerMdns`/`BuildDevices` 给每个实例盖上 `ServiceType`，本地浏览与 server mDNS 表两个来源都能区分 pairing / connect / legacy；`BrowseAsync` 提前命中时返回**整批**结果而非丢弃。

### 改动的文件

- `UotanStudio.Comm/Protocols/Adb/Pairing/AdbQrPairingService.cs`（配对与连接服务共用同一浏览会话、候选轮询与竞速、16 进制/端口选择校验）
- `UotanStudio.Comm/Transports/Udp/AdbMdnsDiscovery.cs`（`WaitForPairingSnapshotAsync`、整批返回、服务类型标记）
- `UotanStudio.Comm/Transports/Udp/MdnsDevice.cs`、`UotanStudio.Comm/Protocols/Adb/AdbServerMdns.cs`（`ServiceType`）
- 手动端口面板保留，仅用于设备**从未广播**连接服务的兜底。

## 二、直连（无 server）ADB 设备日志报错（并行子代理）

两个叠加根因：

1. `UsesSharedAdbSession` 排除了 `"adb-tcp:"`，属性查询因此新建租约，被 logcat 已放进共享池的同端点租约拒绝 → `DeviceEndpointBusyException`。ADB 本就一条连接多路复用，现改为网络直连与 USB 直连共用同一会话（`UotanStudio/Services/Devices/DeviceMonitorService.SharedAdb.cs`）。
2. `AdbConnection.Send/SendAsync` 写失败不置 `_connected=false`，`IsConnected` 恒真 → 已死的 TLS 连接被反复复用（即 `Cannot write application data on closed/failed TLS connection`），logcat 进程名表永远读不到。新增 `InvalidateFailedTransport`，在握手完成后的写失败/异步写超时时立即失效连接（`UotanStudio.Comm/Protocols/Adb/AdbConnection.cs`）；logcat 的 `ps` 查询改为每次按需借用当前池内会话（`UotanStudio/Services/Devices/DeviceMonitorService.Logs.cs`）。

回归测试：`UotanStudio.Tests/Protocols/AdbConnectionFailureTests.cs`、`UotanStudio.Tests/Devices/SharedAdbSessionPolicyTests.cs`；已做反向验证（去掉失效标记后测试失败）。

## 三、验证（Windows x64，.NET 10 Debug）

- `dotnet restore UotanStudio.slnx -p:Configuration=Debug` → 成功；`dotnet build ... -c Debug` → **0 警告 0 错误**。
- `AdbPairingDiscoveryTests` → 29/29（含新增端口选择/地址族匹配/服务类型断言）。
- `--filter-namespace UotanStudio.Tests.Devices` → 256/256；`UotanStudio.Tests.Protocols` → 43/43（含新增 6 条）；`AdbConnectionFailureTests` 2/2、`SharedAdbSessionPolicyTests` 4/4。
- `dotnet format whitespace/style --verify-no-changes`（本次改动文件）→ 无差异。
- `dotnet publish UotanStudio.Desktop -c Release -r win-x64 -p:PublishAot=true` → 成功产出；裁剪/AOT 警告全部来自 Dock XAML trampoline、YamlDotNet、Common.Logging、LTRData 与 Makaretu 的 Linux-only 辅助方法，无一条指向本次改动类型（未与改动前日志逐条基线对比）。
- 环境坑：后台 Release publish 与 Debug 构建并发会复现 `CS1061 AttachDockDebugOverlay`（`Dock.Avalonia.Diagnostics` 的 `IncludeAssets` 按 `$(Configuration)` 求值），重新以 Debug 还原后恢复 0 警告 0 错误。
