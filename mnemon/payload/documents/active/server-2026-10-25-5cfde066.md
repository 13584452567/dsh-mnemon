# 扫码配对端口自动解析：server 目标实例名识别与直连端口重试

相关文档：`a1040553-a8fc-487d-948f-157183fd1cfa`（同一功能线上一轮：配对会话内收集 connect 候选、server 轮询与 `adb connect` 竞速）、`65b080df-c163-4577-8543-ecbb049d88ac`（server 模式 `host:pair` 结果帧与进程内 SPAKE2 回退）、`b1898c91-0104-446e-9ebf-b27f6dcb61c6`（ADB/HDC 远端连接与真机矩阵）。

## 症状

扫码配对本身成功，但连接端口解析几乎在所有机型上都失败：等待窗口耗尽后抛 `AdbQrPairingConnectPortException`，界面弹出“手动输入端口”面板。问题不在手机侧，而是解析侧的系统性缺陷。

## 根因

| 现象 | 根因 |
| --- | --- |
| 设备其实已被 server 自动连接，仍判定“找不到端口” | 现代 adb server（Android Studio 自带）自动 mDNS 连接 `_adb-tls-connect._tcp` 时，把该传输的 serial 记为 **DNS-SD 实例名**（`adb-XXXX._adb-tls-connect._tcp`），而旧的 `TryFindServerEndpoint(host)` 只按 `host:` 前缀匹配 serial。于是“已连上”永远看不到，白等 15 秒后转入手动端口面板。 |
| 配对端点与连接端点对不上 | server mDNS 表解析出的配对端点没有 SRV 主机名，后续本地浏览只能按 IP 匹配；双栈/多网卡下配对服务与连接服务可能落在不同地址族或不同网卡，匹配必然失败。 |
| 直连路线一次探测失败就放弃 | adbd 在配对后重启 TLS 服务，端口在切换瞬间不应答，单次 TCP 探测会误判为无可用端口。 |

## 设计要点

### 有 adb server（server 路由）— `AdbQrPairingService.cs`

- **server 目标身份解析**（`MatchServerConnection`，`AdbQrPairingService.cs:496`）：同时识别 `ip:port` 串号与 `adb-…._adb-tls-connect._tcp` 实例名串号（经 `host:mdns:services` 表解析）；`device` 状态优先于 `unauthorized`，`offline` 忽略。设备已被 server 自动连接时立即复用，不再重复连出第二个传输。
- **未自动连接时的双路并行**（`ConnectThroughServerAsync`，`AdbQrPairingService.cs:361`）：轮询 server 目标列表，同时向每一个广播端口显式 `host:connect`（候选来自配对浏览、server mDNS 表、实时本地浏览）；先 TCP 探测再拨号，避免制造 offline 目标。
- **别名归一抽成公共实现**：`BuildConnectAliases` / `ResolveConnectAlias`（`AdbServerMdns.cs:199`）处理 `.local` 后缀、尾点、裸实例名与全名；`AdbServerDiscoverySource` 复用同一实现，消除两处规则漂移。

### 无 adb server（直连 TLS/TCP 路由）— `AdbQrPairingService.cs`

- **端口探测带重试**（`ResolveDirectConnectPortAsync`，`AdbQrPairingService.cs:693`）：按 SRV 主机名或地址匹配候选后先探测端口；在 20 秒窗口内每 500 ms 重试，覆盖 adbd 重启 TLS 服务的空档，而不是一次失败即放弃。
- **专用安全连接浏览**（`CollectConnectServicesAsync`，`AdbMdnsDiscovery.cs:190`）：窗口内收集全部 `_adb-tls-connect` 实例并支持提前退出。
- **握手失败后的补救**：直连 TLS 握手在“已被设备替换的广播端口”上失败时，按 IP 重新浏览一次当前端口，并以新地址登记为需要 TLS 的手动网络端点；无替代端口时重新抛出原始失败（`VerifySecureNetworkTargetAsync`，`DeviceMonitorService.Pairing.cs:155`）。

### 最后一层兜底

- 确实找不到端口时，异常携带“广播过但未连通”的端口；扫码窗口预填并全选该端口（`QrPairingWindow.axaml.cs:59`），回车即连，无需手打。
- 配对/连接结果写入 GUI 日志（`DeviceMonitorService.Pairing.cs:79`），失败时保留异常类型与消息。
- 轮询阶段的进度映射保持 `WaitingForScan → Pairing → Connecting`（`RunQrPairingAsync`，`DeviceMonitorService.Pairing.cs:44`）。

### 覆盖矩阵

有 server 走 server 目标列表与 mDNS 表；无 server 走原生 TCP + TLS 直连会话；两条路都经 `DeviceMonitorService` 登记为可拨号目标。USB 直写路径未改动，此前的共享会话与“写失败即失效重建”加固继续覆盖 USB 与 TCP 直连（网络直连目标现在同样复用一条会话）。

## 未验证的边界

- 本机没有 Android 11+ 真机，**“扫码后免输端口”的端到端行为未实测**；单元测试只覆盖目标身份解析、别名归一、候选选择与状态优先级。
- 手机在配对后立即撤回 `_adb-tls-connect` 广播、以及纯 IPv6-only 链路上的连接仍未实测。
- `dotnet build UotanStudio.slnx -c Debug` 的 Desktop 拷贝步骤被正在运行的 UotanStudio.Desktop（PID 16836）锁住，改用临时 `OutputPath` 完成 Desktop 编译；**需重启该应用才能看到修复效果**。
