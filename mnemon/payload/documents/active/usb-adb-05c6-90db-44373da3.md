# USB ADB 直连：握手持续收到外来帧的排查状态与新增诊断（05C6:90DB）

## 症状与实测证据

Windows x64 上对 `05C6:90DB`（serial `6b24c48f`，绑定 `iface FF/42/01 ep in 86 out 03`）做 ADB 直连握手时：

- 入站 24 字节头的 `command` 为 `0xEB93D9CA`、`0x79EF7586` 等，均非任何合法 ADB 命令字，且 magic 也不等于命令字取反，说明这 24 字节完全不在 ADB 流里，而不是“从中途开始读一帧”的失步。
- 清空入站管道后重发一次 CNXN 无效；随后 3 次探测（每次上限 300 ms）全部在 **0 ms** 就拿到新的 24 字节外来数据，内容每次不同、高熵。
- 全新启动应用、不启动投屏、直接打开设备详情，仍然乱码。
- 同一台设备 `adb devices` 能看到（可用），但直连不行。

## 已排除的原因

- **残留投屏会话仍在传输**：`UotanStudio.Mirroring` 对 `DeviceLease`/`GetStream()`/`UsbStream` 的引用数为 0；投屏数据只能作为 ADB `WRTE` 帧载荷走同一条 ADB 连接，不可能在帧头位置产生非法字节。
- **残留脏字节（一次性失步）**：脏字节会表现为“重发后端点静默”，而实测是 0 ms 持续输出（full rate），属于另一条数据流。
- **旧 reader 未退出、与新会话分食同一管道**：全新启动后仍复现，且此时没有旧会话。

结论：要么设备当前复合里 adb 功能未激活（读到的更像厂商诊断/QCDM 类流），要么批量端点对选错（`86/03` 反常，常规 ADB 对是 `81/01`）。两者靠 `adb devices -l` 区分。

## 判定路径（下一步唯一需要的输入）

1. `adb devices -l`：若列出 `host:port`（如 `192.168.x.x:5555`）→ 手机的 USB adb 功能在当前复合里没起来，adb 走网络；问题在设备侧（重开“USB 调试”、撤销授权、重插），程序侧只保留明确报错。
2. 若列出 USB 序列号 `6b24c48f` → adb server 能驱动同一接口而本库不能，属于端点对选择缺陷，修法：优先 `0x81/0x01` 配对，CNXN 无响应时换下一组 bulk 对重试。
3. 桌面侧交叉验证：失败后等 10–15 s 再连一次；用设备管理器确认 `05C6:90DB` 是手机本体还是诊断/下载类设备。

## 本轮新增的诊断能力

- **失败日志追加接口清单**：`WinUSBDevice` 早已解析整份配置描述符，却只上报“被绑定的那个接口”，其余被丢弃。现在 `UsbDevice.EnumeratedInterfaces`/`UsbDeviceInfo.EnumeratedInterfaces` 保存全部接口（经 `UsbDeviceInfoFactory` 传递），每条握手失败日志后追加
  `descriptor interfaces: #NN class/sub/proto eps [0x86/02/512B, 0x03/02/512B]; …`，
  一条日志即可回答“`0x86/0x03` 是否属于 `FF/42/01`”和“是否还有别的候选接口”。
- **探测语义显式化**（`AdbConnection`）：一次性重同步用掉后做最多 3 次短读，逐次记录到达耗时与十六进制：
  - 300 ms 内无更多字节 → 端点空闲，首帧只是残留脏字节；
  - `probe k/3: still foreign after X ms` 连续出现（尤其 0 ms）→ 端点持续流出非 ADB 数据，设备侧或外部占用；
  - 拿到合法 ADB 头 → 对端恢复，该帧被探测吃掉，重建会话即可。
- **同传输多读者检测**（`UsbDeviceTransport`）：同一条传输出现第二个入站读者时以 Debug 级打印
  `transport #N (05C6:90DB serial …) now has K concurrent inbound reads on the same bulk pipe; one ADB stream is being split between readers…`，把“一帧被两个读者切开”从猜测变成可直接观测。
- 记下 `UsbDeviceSession` 的并发模型：读/写/控制传输各用一把独立门闩（`_readGate`/`_writeGate`/`_controlGate`），同向严格串行、异向可全双工；`Dispose` 通过 `Interlocked.Exchange(ref _disposed, 1)` 幂等，并先取 `_readGate` 再释放设备，避免读到一半被拆除。

## 编译期踩到的坑（本仓库约定相关）

- `UsbInterfaceInfo` 位于 Comm 的 USB 抽象命名空间，`AdbConnection.cs` 里直接使用会 `CS0246`，需要补 using。
- 新加的 XML 注释写成第二个 `<summary>` 并在其上写 `<param name="header">` 会触发 `CS1572`（该参数不在签名里）；`AdbConnection` 已开文档文件生成，注释必须按 `summary → param → returns` 单块组织。

## 验证（Windows x64，Debug）

- Comm 构建 0 警告 0 错误；改动文件 `dotnet format` whitespace 与 style 零报告。
- `UotanStudio.Tests.Devices` 247/247、`Protocols` 37/37、`UsbStreamWriteTests` 2/2 通过；测试运行器仍报退出码 2（`/testingplatform/exitcodes`），但失败数为 0，此为既有现象。

## 未验证边界

- 新增的三类日志都还没有在真机上产生过一次；它们能否区分“复合模式错误”与“端点对选错”只有设计层面的推理，没有实测样本。
- 真实设备上 `0x86/0x03` 是否属于 `FF/42/01` 接口、配置描述符里是否还存在 `81/01` 候选对，都还没拿到 `descriptor interfaces:` 实测行。
