# 无 mDNS 广播时的直连端口发现：有界 TCP 扫描 + ADB 握手校验（2026-10-27）

本轮真机现象：无 adb server 的扫码配对，配对本身成功，但随后解析连接端口失败，日志为
`AdbQrPairingConnectPortException: The device did not answer on any advertised secure connect port for 192.168.1.144 (tried ports []; observed '_adb-tls-connect._tcp.local' instances [none])`。
`tried ports []` 是关键：候选端口列表为空，即组播浏览与单播 DNS-SD 问询都没有交出任何实例。

## 真机证据（Windows x64，Debug，无 server）

对 `192.168.1.144` 逐项探测：

| 探测 | 结果 |
| --- | --- |
| 组播 PTR `_adb-tls-connect._tcp.local` | 无应答 |
| 单播 DNS-SD 问询（设备 :5353） | 无应答 |
| 扫描 32768–60999（28232 个端口，约 51 s） | 仅 `44065` 开放 |
| 向 `:44065` 发 ADB `CNXN` | 首帧 `STLS`（`0x534c5453`，`arg0=0x01000000`，magic 正确，TLS） |
| 用本机身份链对 `:44065` 完成 ADB 握手 | 成功（设备已信任本机密钥） |

结论：端口一直在监听，缺的只是广播——QR 配对/换端口后 adbd 不重播 `_adb-tls-connect` 属设备侧行为，主机侧无法靠等待修复。此前的兜底（组播浏览 → 30 秒持续重读 → 单播 DNS-SD 问询，见文档 `b3f83b64-e6de-4c4f-b765-00d33be373e2`）在两者都无应答时只能抛异常要求手填端口。

## 设计要点

- **`UotanStudio.Comm/Transports/Tcp/TcpPortScanner.cs`**：有界并发 TCP 探测。并发度、单次连接期限、整体预算与 `CancellationToken` 全约束；提供「命中即结束整轮」的接受回调，避免扫满全范围。
- **`UotanStudio.Comm/Protocols/Adb/AdbSecureSessionFactory.cs`**：把原先分散在 `DeviceController` 的「用本机身份链派生证书打开安全会话」抽成共用入口，扫描与正式连接走同一套 TLS 会话构造，避免行为漂移。
- **`UotanStudio.Comm/Protocols/Adb/Pairing/AdbQrPairingService.cs`**：`ResolveDirectConnectPortAsync` 在组播 + 单播都拿不到端口后，扫描 `32768-60999`（Android 默认临时端口范围）。**每个开放端口必须完成一次 ADB 握手才被接受**，因此设备上无关的开放端口（HTTP 调试口等）不会被误认作 adbd；命中即继续建立连接。全失败时异常消息附带扫描结果，手动端口面板预填扫描到的最小监听端口。
- **`UotanStudio.Comm/Devices/Services/DeviceController.Inventory.cs`**：改用共用工厂，保持 `OpenSecureNetworkAdbSession` 契约不变。
- 界面文案新增/复用了 `UotanStudio/Locale/Common.resx` 与 `Common.zh-CN.resx` 的中英条目。

## 验证

- `dotnet build UotanStudio.slnx -c Debug`：0 警告 0 错误；`dotnet format` whitespace 与 style `--verify-no-changes` 通过。
- 新增 `UotanStudio.Tests/Devices/TcpPortScannerTests.cs`：7/7 通过（命中提前结束、预算与取消、无监听端口）。
- `UotanStudio.Tests.Devices` 312 项：309 通过；2 项在整批并发下超时/取消（`AdbTlsTransportTests.UpgradeToTls_DeviceRebuildsItsCertificateEachHandshake_CompletesBothHandshakes`、`HdcServerTransferTests.Recv_RegularFile_PublishesOnlyAfterCompletion`），单独复跑分别 6/6、10/10 通过，与本次改动无关。
- 真机：用新的 `AdbSecureSessionFactory` + `AdbSession.ConnectAsync` 在 `192.168.1.144:44065` 完成握手。

## 未验证边界

- 没有在同一时刻重跑完整扫码流程（需手机当场扫码），「配对 → 扫描 → 连接 → 登记目标 → 投屏」端到端链路未复测；文档 `cd5e7bab-64ff-4918-887a-bab9cd978987` 记录的配对后 adbd 重启 TLS 服务导致旧会话失效问题仍可能叠加出现。
- 扫描只覆盖 IPv4 与 Android 默认临时端口范围；IPv6-only 链路或改过 `ip_local_port_range` 的设备不在覆盖内。
- 失败路径会在抛异常前向设备发起最多约 2.8 万个短连接，企业 Wi-Fi 的入侵检测可能告警；未做速率/告警评估。

细节与实测数字同步写入仓库 `VERIFICATION.md`（「扫码后的连接端口自动获取」条目）。
