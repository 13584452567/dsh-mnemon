# USB 接管驱动（WinUSB 接管）安装后设备无法启动：逐方法对照 libwdi 的根因分析（2026-11）

## 症状

接管驱动安装完成后，设备管理器内该驱动**无法卸载、升级、删除设备**，其他 USB 设备的枚举也被阻塞；只有把被接管的硬件物理移除后，设备树才释放并恢复正常枚举。

## 结论（一句话）

四个症状是同一条主线的不同侧面：**接管把一次 PnP 安装拆成「现在暂存包 + 稍后排队安装」，再用固定 180 s 硬超时去杀正在安装的助手，全程没有任何一步等待 PnP 安装事务走到终态。** libwdi 对应的做法是「同步重枚举 + 安装阶段无限等待 + 只处理已拔出的幽灵节点」。

## 逐方法对比（关键差异）

| 方法 | libwdi | 当前实现 | 后果 |
|---|---|---|---|
| 安装入口 | 先 `UpdateDriverForPlugAndPlayDevices(FORCE)`，失败才 `SetupCopyOEMInf` 兜底（`reference/libwdi/libwdi/installer.c:876` / `:895`） | 先 `SetupCopyOEMInf`（`UotanStudio.Comm/Transports/Usb/Drivers/WinUsbDriverInstaller.cs:257`），再按 problem 分支 | 包先成为仓库里的候选驱动，之后每次枚举都可能自动装它，失败也无回滚 |
| `RequestRebind` | `CM_Reenumerate_DevNode(RETRY_INSTALLATION)` **同步**，返回值即结果（`installer.c:262`） | 加 `ASYNCHRONOUS`（`WinUsbDriverInstaller.cs:449-451`），`CR_SUCCESS` 只等于「已入队」 | 安装被移交 PnP 安装线程，之后再没人等它；失败安装意图留在 devnode 上，每次枚举重跑 |
| 等待/超时 | 助手用 `IC_SET_TIMEOUT_INFINITE` 让父进程在安装阶段无限等，只在**失联**时杀（`reference/libwdi/libwdi/libwdi.c:1665-1671`、`:1947-1951`） | 父进程固定 180 s 后 `Kill(entireProcessTree)`（`UotanStudio/Services/Devices/UsbDriverConfigService.cs:275-310`，`ElevatedTimeout = 180s` 于 `:110`） | 超时所有权错位：不知道进度的一方单方面杀掉正阻塞在 PnP 安装里的进程 |
| 包生命周期 | 安装期间**从不**删包 | `finally` 无条件删工作目录（`WinUsbDriverInstaller.cs:304`） | 异步安装还在进行，安装源已消失 |
| 结束接管 | libwdi 无卸载入口；业界做法先解绑再删包 | 先 `SUOI_FORCEDELETE` 删 **live** oemXX.inf → 再删**全部**同主体证书 → 再异步重枚举 → 立即报成功（`WinUsbDriverInstaller.cs:384-399`） | devnode 的 DriverInfPath 悬空 + 全部历史接管包同时失去信任 = 无法卸载/升级/删除设备 |
| 证书 | 主体 `CN=<hw_id> (libwdi autogenerated)`，一 HWID 一证书（`libwdi.c:1561`） | 全局常量主体，全设备共用（`WinUsbSelfSignedDriverPackage.cs:37-38`），释放时删光 | 一次释放让所有接管包失效，只能拔设备 |
| `IsRemovalPending` | — | `0x10000/0x20000` 实为 `DN_MF_PARENT/DN_MF_CHILD`（`WinUsbDriverInstaller.cs:487-490`） | 复合设备被误判「移除中」而拒接，真实冲突反而漏检 |
| 批量重枚举 | `check_removed` 只给**已拔出**的匹配幽灵节点写 `CONFIGFLAG_REINSTALL`（`installer.c:277-334`） | 遍历全部在位节点，最多 128 个异步重枚举（`UotanStudio.Comm/Transports/Usb/Drivers/DriverPackageInstaller.cs:34`、`:285-330`） | 一次点击向 PnP 排入上百笔安装，是整个 USB 树卡住的放大器 |
| 待安装准入 | `CMP_WaitNoPendingInstallEvents`（`libwdi.c:1710-1768`；Zadig 传 0 = 有他人安装立即退让） | 无 | 缺同 HWID 互斥与准入，与设备安装串行化锁冲突 |

## 排查掉的假因

- **INF 合法**：对过本机 `C:\Windows\INF\winusb.inf`，`[WINUSB.NT.HW]` 就是空占位，`[WINUSB.NT.Services]` 就是 `AddService=WINUSB,0x2,WINUSB.AddService`；当前生成包结构与之一致。
- **签名/CAT 不是主因**：CAT 与 Authenticode 流程与 libwdi 同构，且 `winusb.sys` 是微软在箱签名二进制；签名失败会在暂存/安装阶段直接报 `ERROR_AUTHENTICODE_PUBLISHER_NOT_TRUSTED`，不会表现为「绑上了但没启动」。

## 归因链

- **P0-1 事务两段式**：`CM_REENUMERATE_ASYNCHRONOUS` 排队 → 30 s 轮询「绑定是否变样」→ 删包 → 进程退出。devnode 停在 `CM_PROB_FAILED_INSTALL`(0x1C)，而 `RETRY_INSTALLATION` 意图让它每次枚举重跑一次注定失败的安装。
- **P0-2 180 s 硬杀**：`UpdateDriverForPlugAndPlayDevices` 在调用进程内同步完成 stop→install→start（类安装器/co-installer 就在该进程里跑），杀掉后事务无回滚路径，devnode 停在「安装中/待重启」，设备管理器三条路径全部无解。
- **P0-3 拆除顺序倒置**：先删 live INF、再删全部证书、最后才重枚举。
- **P1 放大器**：缺 `CMP_WaitNoPendingInstallEvents` 准入；缺设备句柄检查与同 HWID 互斥；失败安装 + 排队重试共同占用设备安装串行化锁，只有物理移除能强制该 devnode 的 stop/remove/start 走完终态——这正是「拔掉设备才恢复」的指纹。

## 修复优先级

1. 安装改回 libwdi 顺序（先 force 装、失败再暂存）+ **同步** `RETRY_INSTALLATION`（去掉 `ASYNCHRONOUS`）+ 轮询 `DN_STARTED`/`problem==0` + 安装期间不删包。
2. 去掉固定 180 s 硬超时，改成「助手心跳失联」判定，绝不在安装进行中 `Kill`。
3. 结束接管改为 `DiUninstallDevice`/`DiUninstallDriver` 先解绑，再 `SetupUninstallOEMInf(inf, 0)`（不带 `SUOI_FORCEDELETE`），证书最后删且按 HWID 区分。
4. 修正 `DN_QUERY_REMOVE_*` 常量与 `IsRemovalPending`；给厂商包路径的重枚举加匹配过滤与个位数上限。

## 未验证边界

- 未在真实设备上复现：具体 problem 码（0x0A / 0x1C / 0x25 / 0x26）决定是 P0-1 还是 P0-2 为主。
- 「杀进程留半事务」属机制推断，未用内核调试器确认阻塞链最后一环（设备安装锁 vs 设备树锁的持有者）。
- 取证办法（问题码、`SetupAPI` 日志、devnode 属性、驱动安装事件）记录在完整分析稿 `artifacts/driver-takeover-libwdi-comparison.md` §5。
