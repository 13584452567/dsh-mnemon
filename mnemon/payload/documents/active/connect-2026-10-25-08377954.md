# 扫码配对后用旧连接端口连不上（2026-10-25）

相关文档：`a1040553-a8fc-487d-948f-157183fd1cfa`（配对后自动发现连接端口、共享 ADB 会话）、`5cfde066-d749-4e66-8f39-c819d853361e`（server 实例名识别与直连端口重试）、`65b080df-c163-4577-8543-ecbb049d88ac`（`Unable to start pairing client` 与进程内 SPAKE2 回退）。

## 症状

扫码配对成功了，但随后的连接接口/日志里 **IP 正确、端口是配对前的旧端口**，有 adb server 与无 server 两种情况都连不上。

## 根因（三处把旧端口固化下来）

1. **直连路由**：`AdbQrPairingService.ResolveDirectConnectPortAsync` 只做 **一次**实时浏览，之后就在循环里反复探测同一批已知端口（`Task.Delay` + 再探测），期限内不再浏览。手机配对后以新端口重新广播 `_adb-tls-connect._tcp`，那次浏览早于重新广播就永远看不到新端口。
2. **server 路由**：`ConnectThroughAdvertisedPortsAsync` 只要第一次浏览得到的端口都试过就直接 `return null` 交给手动端口回退，而手动回退预填的又是 **配对前快照**里的端口。
3. **`host:connect:` 的假成功**：adb 只要 TCP 能建连就回 `connected to ip:port`，不等 ADB 握手；一个“能建连但不是 adbd”的端口会被当成连接成功，于是不再尝试后续端口。
4. 附带显示问题：进度文案“配对成功，正在连接 {0}”填的是**配对端点**（配对端口），界面/日志看起来就像“端口解析错”。

## 修复（`UotanStudio.Comm`）

- **配对后持续重新浏览**：两条路由都改为每 3 秒浏览一次、直到 20 秒期限，不再“一次浏览就放弃”；新端口按来源（配对浏览会话快照 → server mDNS 表 → 反复实时浏览）依次尝试，已试端口去重。
- **候选排序“最近广播优先”**：`SelectConnectPorts` 先按 SRV 最近收到的时刻（`MdnsDevice.LastSeenUtc`，`DeviceAccumulator` 新增并在收到记录时刷新）倒序，再按“地址命中优先于仅共享 SRV 主机名”排序——重广播后新端口排在最前。
- **连接成功要复核**：`host:connect:` 返回后用 `host:devices-l` 轮询最多 2 秒，目标必须不是 `offline` 才接受，否则继续试下一个端口（`ConnectServerEndpointAsync` / `WaitForExplicitTargetAsync`）。
- **手动端口预填用最新值**：先做 2 秒实时浏览取最新广播端口，再退回快照/server 表。
- **配对端口失效重试**：直连配对若失败在 TCP 连接阶段（`SocketException`），重新解析端点后重试一次，覆盖“重复扫同一张码、手机换了配对端口”。
- **重新发现也取最新**：`WaitForConnectServiceAsync` 收集整个窗口并返回最近广播的实例（主机侧握手失败后的重试用它）。
- **“正在连接”只显示主机**，不再把配对端口当成连接端口展示。

改动集中在 `UotanStudio.Comm/Protocols/Adb/Pairing/AdbQrPairingService.cs`、`UotanStudio.Comm/Transports/Udp/AdbMdnsDiscovery.cs`、`UotanStudio.Comm/Transports/Udp/MdnsDevice.cs`；`VERIFICATION.md` 同步更新端口行为说明与实测结论。

## 未验证的边界

- 本机没有 Android 11+ 扫码环境，**“配对后换端口”的时序只能由真机验证**；单元测试只覆盖端口选择、排序与结果复核逻辑。
- 生效前必须先关闭正在运行的 `UotanStudio.Desktop`（否则 `bin/Debug` 被锁，新代码进不去）再重建。
- 定位失败时应收集：`QR pairing failed: <异常类型>: <消息>` 或 `QR pairing connected <ip:port> through the ... route`，以及手机“无线调试”页面当时显示的 `IP:端口`。
